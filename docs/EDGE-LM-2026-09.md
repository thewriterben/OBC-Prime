# Language models on the node — September 2026

A capability survey, not a plan. The question was whether a language model can
run on the ESP32 class of hardware OBC already fields, and what it could do if it
did. Every number below is cited; where the only source is press coverage of a
project rather than the project's own measurements, that is said.

Read alongside `RESEARCH-2026-07.md` (where OBC sits) and `DECISIONS.md`
(2026-09-13, *No language model on a node*), which this document is the evidence
for.

---

## The answer, up front

**On the ESP32-S3 boards on the bench, a language model that follows
instructions has not been demonstrated at usable speed by anyone.** What has
been demonstrated is a sub-1M-parameter dense core generating TinyStories prose
at ~10 tok/s, and a real 135M instruct model at 45 minutes per answer. Nothing
in between exists. On the ESP32-P4 there is exactly one project that follows
simple instructions at ~9 tok/s, and its own author calls its tool-calling
unreliable.

Espressif's own answer to "agent on an ESP32" is ESP-Claw: a local rule/memory
runtime that calls an external model endpoint for reasoning. That is
architecturally what OBC's gateway-plus-spinal-tier design already is.

Three of the seven are on the exact board class OBC already runs (S3 N16R8).
None of those three follows an instruction.

## 2. The physics, measured on an N16R8

slvDev's `RESULTS.md` is the one source in this survey with bench numbers rather
than a demo video. All from `firmware/bandwidth_bench`, Xtensa cycle counter,
2026-07-21 [2]:

| Measurement | Value |
|---|---|
| PSRAM sequential read | 60.7 MB/s |
| Internal SRAM sequential read | 240 MB/s |
| Flash random read, 512 B row | 20.3 µs |
| Per-token cost of the 25M-row flash table (6 random rows) | ~0.12 ms |
| Per-token cost of the output head (1.5 MB PSRAM scan) | ~17.3 ms |

What that produces at runtime: 102.9 ms/token, of which the output head is
57.6 ms — and ~40 ms of that is a PSRAM bandwidth floor (2.43 MB of int8 weights
per token at 60.7 MB/s). His conclusion, and it is the one that matters for
anyone sizing a model for this chip: the S3's few SIMD intrinsics would buy a
bounded ~15%; the real levers are *bytes read per token* (int4 head, smaller or
factorised head), not compute. The 58 tok/s figure is a bandwidth ceiling that
the scalar runtime gets nowhere near.

He is also explicit about what the parameter count means: *"Quote it as
parameters resident via a memory-hierarchy split, never as a capability
multiple."* The 25M table improves TinyStories perplexity by 9.3% over a
same-core baseline; it does not add world knowledge, arithmetic or reasoning,
because those are bounded by the 559K dense core.

## 3. The three tricks everything converges on

Every project above that exceeds ~1M parameters uses at least one of these:

1. **Flash-resident per-token lookup tables** (Gemma 3n's per-layer embeddings).
   Most of a small LM's parameters are its embedding table; only the rows for
   the current token are needed, so the table lives in memory-mapped flash and
   costs ~0.7% of per-token memory time [2]. This is why 28.9M "fits" in 512 KB
   of SRAM.
2. **Ternary or INT4 weights with group scales.** slvDev measured that 4-bit
   PTQ degrades the PLE model *less* than the small dense baseline (+0.06 vs
   +0.08 nats), because a large redundant table quantises more robustly than a
   small core where every weight is load-bearing [2]. `p-for-llm` and
   `atome-lm` use BitNet-style ternary.
3. **Mixture-of-experts with top-1 routing**, so only one expert's weights are
   fetched per token per layer. `espllm` and `p-for-llm` both use it. It
   converts the byte-bandwidth problem into a flash-capacity problem.

The P4 project stacks all three and is the first to get instruction-following
at usable speed. It needs the P4's 32 MB PSRAM and 400 MHz RISC-V with FPU, and
currently loads 44 MiB of weights over USB at boot; SD autonomy is listed as
future work [5].

## 4. What Espressif ships

- **ESP-Claw** (Apr 2026): a "chat coding" agent runtime for ESP32 — Lua rules,
  MCP links, local memory, messaging integrations — that calls an
  OpenAI/Anthropic-compatible endpoint for reasoning. People run it against home
  Ollama. It is not on-chip inference and does not claim to be [8][9].
- **ESP LLM solution page**: explicitly cloud inference [10].
- **ESP-DL**: conv/GEMM operators with a static memory planner and dual-core
  Conv2D scheduling — vision-shaped, no transformer kernels [11].

So the vendor's position matches what OBC already built: the node runs rules
and calls out.

## 5. Where OBC's existing design sits against this

The four documents below live upstream in `Oh-Ben-Claw/docs/`, not in this repo.

- `V2-STRATEGY.md` §F asks for a "small-model reflex tier" — and puts it on the
  SBC via local Ollama (`edge.rs`), not on the MCU. That was the right call
  and this survey confirms it.
- `V2-IMPLEMENTATION.md` plans an int8 wake-word spotter via ESP-NN on the S3.
  That is mature TinyML, not an LM, and is unaffected by anything here.
- `CONNECTOME-2026-09.md` §2.2 gives the node a *descending command* that is a
  small modulation vector, not free text. That vocabulary is orders of
  magnitude narrower than ChatML, which is the one thing that would make a
  task-specific on-device model conceivable — see §7.
- `ACCELERAPP-CROSS-POLLINATION.md` already warns Accelerapp's `tinyml_agent`
  is placeholder codegen. Still true; nothing here changes it.

## 6. Honest ceilings by board

**ESP32-S3 N16R8 (on the bench).** ~1M dense parameters at ~10 tok/s with no
instruction-following, or a real instruct model at minutes per token. 8 MB
PSRAM, 60 MB/s to it, no vector unit worth the name. Demonstrated, measured.

**ESP32-P4.** 180M ternary MoE that follows simple instructions at ~9 tok/s,
sometimes. 32 MB PSRAM, FPU, $6–10. Not measured by anyone independent. No
WiFi/LoRa on-chip: a P4 node needs a companion radio MCU, which is a different
node design from the S3/Heltec class OBC has provisioned, authenticated
(SPINE-AUTH) and replay-protected (SPINE-REPLAY).

**Anything Linux-class** (NanoPi, Pi, Jetson) is already covered by `edge.rs`
and is out of scope here.

## 7. Open questions

Recorded so they are not re-derived. None is scheduled; the decision in
`DECISIONS.md` says why.

1. **Would a task-specific model for the modulation vocabulary fit the S3?**
   Answered the same day by reading the code instead of the survey: yes,
   trivially, and it is not a language model. A `descend` is ≤16 levels in
   `[0, 1]` (`obc-reflex`, firmware `reflex.rs`); the only producer is a
   one-bit policy, novel → cautious (`obc-agent/src/posture.rs`); a node
   would produce it from its own sensor snapshot (`ev` on every reflex
   report). That is a few-dozen-weight map, which no trick in §3 is needed
   for. TinyLLM [12] and TinyAgent [13] are about the wrong object. What is
   missing is a metric and data — see `DECISIONS.md` 2026-09-13 and the
   harness `Oh-Ben-Claw/crates/obc-memory/tests/posture_real_effect.rs`,
   which names three candidate metrics.
2. **What does *this* N16R8 measure?** Was the prerequisite to Q1; no longer
   is. slvDev's `bandwidth_bench` would still be the right harness if a
   *language* model were ever proposed for a node, and none is.
3. **Does the P4 change the node design or just the node?** A P4 plus a radio
   MCU is two chips, two firmwares and a UART between them — the unauthenticated
   serial wire `DECISIONS.md` 2026-09-13 already flags for the bridge. Worth
   deciding before buying a board, not after.
4. **Is there any per-node task where 9 tok/s of shaky ChatML beats a Lua rule?**
   ESP-Claw's bet is no. Nothing found in this survey contradicts it.
